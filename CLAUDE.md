# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Valeterna** — a Spanish-language, terminal-based turn-based RPG written in Python. Uses `colorama` for colored terminal text and `pygame` (mixer only) for background music/SFX — there is no graphical window, the game is played entirely via `input()`/`print()` in the console.

Packaged as an installable Python package (`src/` layout) under `src/valeterna/`.

## Commands

Setup (Windows, PowerShell):
```powershell
python -m venv env
.\env\Scripts\activate
pip install -e ".[dev]"
```

Run the game:
```bash
python main.py
# or: python -m valeterna
# or, after install: valeterna
```

Run tests:
```bash
pytest
pytest tests/test_battle.py::test_defeat_penalizes_gold_and_fully_heals_player   # a single test
pytest -k "mago and heal"                                                        # by keyword
pytest --cov=valeterna --cov-report=term-missing       # with coverage
pytest --cov=valeterna --cov-report=html               # htmlcov/index.html
```

Lint / format / types (config in `pyproject.toml`):
```bash
ruff check .           # lint — F, E4/E7/E9, W, I, UP, B, SIM
ruff format .          # or `ruff format --check .` in CI
pyright                 # basic mode, `src` only, must stay at 0 errors
```

## Project meta

- **Docs are bilingual**: English originals at the repo root (`README.md`, `CHANGELOG.md`, `CONTRIBUTING.md`, `ROADMAP.md`, `GDD.md`, `CODE_OF_CONDUCT.md`, `SECURITY.md`), Spanish translations under `docs/*_es.md`, each with a language switcher at the top. `CLAUDE.md` and `TODO.md` are not translated (CLAUDE.md is tool-facing; TODO.md is the Spanish balance-tuning log). `GDD.md` is the design doc for the planned world/story/RPG direction (see the "Planned — phased plan" in `ROADMAP.md`); nothing in it is built yet.
- **CI** (`.github/workflows/ci.yml`): on push to `main` and every PR, runs `ruff check`, `ruff format --check` and `pytest --cov`. The `test` matrix is Python 3.10–3.13 on **Linux** plus one **Windows** job (3.12) for the `msvcrt` path and pygame-on-Windows. A separate `types` job runs `pyright` (basic mode, `src` only — currently 0 errors; `reportIncompatibleMethodOverride` is off because the `Item`/`Player`/`Enemy` hierarchies use deliberate duck typing). The `all-green` job aggregates `test` + `types` into the one status check the `main` branch ruleset requires. A `coverage-badge` job (push to `main` only, on Linux) regenerates the coverage SVG with `genbadge` and pushes it to the orphan **`badges` branch** — kept off `main` so it doesn't need a PR through branch protection; the README links `raw.githubusercontent.com/.../badges/coverage.svg`.
- **Branch protection**: `main` has a ruleset requiring a PR (0 approvals) with the `all-green` check green. Work on a branch, open a PR, let CI pass, merge.
- **Coverage** (`[tool.coverage.run]` in `pyproject.toml`): `ui/menus.py`, `ui/exploration.py` and `app.py` are `omit`ted — they are interactive menu loops / startup orchestration, mostly chained `input()`/`print()` calls; the metric tracks the game logic instead. Target is ≥90% of the measured code.
- **Release** (`.github/workflows/release.yml`): pushing a `v*` tag builds the PyInstaller package from `Valeterna.spec` (now version-controlled), zips `dist/Valeterna`, and attaches it to the GitHub Release. `.github/scripts/write_secrets.py` writes `config/secrets.py` from repo secrets first (skipped if none set). See `CONTRIBUTING.md` for the full release steps.
- **Build check** (`.github/workflows/build-check.yml`): only when packaging files change (`Valeterna.spec`, `main.py`, `pyproject.toml`, …) — builds the `.exe`, runs it with stdin `4` (menu "Salir") expecting exit 0, and uploads the folder as an artifact. Not a required check.

## Architecture

**Entry point**: `main.py` at the repo root is a thin compatibility shim that calls `valeterna.app.main()`. The real entry point is `src/valeterna/app.py::main()`, which first force-reconfigures `sys.stdout`/`sys.stderr` to UTF-8 (a plain Windows console defaults to a legacy code page that can't encode the emoji used in menu titles — this bit only surfaces outside a UTF-8-safe terminal like PyCharm's, e.g. a packaged `.exe` run from `cmd.exe`, so it's easy to miss in normal dev use), initializes `colorama`/`pygame`, loads saved volume settings (`config/settings.py`), registers all audio assets (`audio/catalog.py`) with `ResourceManager`, then hands off to `ui/menus.py::main_menu()`. Menu "exit" options call `sys.exit()`, not the bare `exit()`/`quit()` builtins — those are `site`-module REPL conveniences that don't exist in a frozen PyInstaller build.

**Error logging (`config/logging_setup.py`)**: `setup_logging()` (called at the very top of `app.main()`) wires a `RotatingFileHandler` at `BASE_DIR/logs/juego.log` (next to the `.exe` when frozen), installs `sys.excepthook` + `threading.excepthook`, and logs a session-start banner (game version / Python / platform). Any unhandled exception — the `except Exception` in `app.main()`, or one that escapes entirely — goes through `report_crash()`, which writes the full traceback both to the rotating log and to a standalone `logs/crash_<timestamp>.txt`, and `app.main()` then prints that path and holds the window open with an `input()` so a packaged-`.exe` player can actually read it before the console closes. `logs/` and `crash_*.txt` are git-ignored. Tests: `tests/test_crash_logging.py`.

**Auto-update (`updater.py`)**: only in the frozen build and outside CI (`updater.is_active()` = `sys.frozen and not $CI`). `app.main()` starts `updater.start_background_check()` (daemon thread, same pattern as `_music_watchdog`) if `settings.load_update_check()` ([UPDATES] check_on_startup, default on). The thread does `cleanup_staging()` then `check()` — a plain `urllib` GET to `api.github.com/.../releases/latest`, compares `tag_name` to `__version__` by numeric tuple (`_version_tuple`), and only stores an `UpdateInfo` if strictly newer and there is a `*-windows.zip` asset. `ui/menus.py::_maybe_show_update_notice()` prints a one-line notice once per session in both menu loops. Options has a manual "Buscar actualizaciones ahora" and the on/off toggle. `check()` never raises; a failed check keeps a previously-found result. When `updater.available()` is set, `main_menu()` shows a dynamic "Actualizar a {tag}" option → `_update_flow()`: shows the notes, confirms, then `download_and_stage(info)` (streams the zip to `BASE_DIR/.update/download.zip`, `verify()`s its SHA-256 against the `SHA256SUMS` release asset — refuses if absent — and `zipfile.extractall`s to `.update/new/`, returning `.update/new/Valeterna`) and, on success, `apply_and_restart(new_dir)` (writes `.update/apply.bat`, launches it with `os.startfile` — ShellExecute, fully async and detached, after `subprocess.Popen` + `CREATE_NEW_CONSOLE` was found to intermittently `0xC0000142` when spawned during the game's teardown — waits ~1.5s, then `sys.exit(0)`). The `.bat` waits for the game process to exit (by **image name** via `tasklist | find /i Valeterna.exe` — matching the bare PID could collide with other `tasklist` columns), then `robocopy /MIR`s the new build over `BASE_DIR` — mirror, not copy, so stale files like the previous version's `*.dist-info` (which kept `importlib.metadata` reporting the old `__version__`) are removed — protecting `saved_games/`, `logs/`, `.update/` (`/XD`) and `config.ini` (`/XF`), guards that both `SRC` and `DST` hold a `Valeterna.exe` before mirroring, relaunches the game, and leaves an `apply.log` next to the `.bat`. `.update/` is wiped on the next launch by `cleanup_staging()`. Network/subprocess branches are `# pragma: no cover`. Threat model (HTTPS + SHA-256 protect integrity, not a compromised GitHub account) in `SECURITY.md`. `release.yml` writes `SHA256SUMS` next to the zip. Tests: `tests/test_updater.py`.

**Secrets (`config/secrets.py`)**: git-ignored, holds `CRASH_WEBHOOK_URL`, `CRASH_MENTION_USER_ID`, `ADMIN_PASSWORD_HASH`. `config/secrets.example.py` is the committed template (all keys blank). `config/secret_store.py` is the tolerant accessor — `secret_store.get(name, default="")` returns the default (never raises) when `secrets.py` is absent, so a fresh clone runs fine with crash-reporting and admin mode simply disabled. `ui/menus.py::_ADMIN_PASSWORD_HASH` and everything in `config/crash_reporting.py` read through it.

**Optional crash reporting to Discord (`config/crash_reporting.py`)**: opt-in, off by default, no third-party service — a plain `urllib` multipart POST of the (path-scrubbed) `crash_*.txt` to a Discord webhook, same pattern as the user's "Vektra" bot. Webhook URL resolves env `JRT_CRASH_WEBHOOK` → module constant `WEBHOOK_URL` (blank in repo) → `secrets.py::CRASH_WEBHOOK_URL`. A custom `User-Agent` header is mandatory — Discord 403s urllib's default. If `CRASH_MENTION_USER_ID` (numeric) is set, the message is prefixed with `<@id>` and `allowed_mentions` is scoped to that id (so an error string can never smuggle in an `@everyone`). `scrub()` strips the OS username and home-dir paths before anything leaves the machine. If `is_configured()` (a URL is set) and the player hasn't answered yet, `app.main()` calls `ui/menus.py::ask_crash_reporting_opt_in()` once at startup; the choice persists in `config.ini` `[REPORTS] send_crash_reports` (`settings.load_crash_reporting()` returns `True`/`False`/`CRASH_REPORTS_UNSET`) and is toggleable under "Opciones" (that menu option only appears when a webhook is configured). `send_crash_report()` never raises (network down / bad URL just returns `False`; the local log still has everything). Tests: `tests/test_crash_reporting.py`.

**`config/` — centralized paths and settings**: `config/paths.py` resolves `BASE_DIR`/`ASSETS_DIR`/`SAVE_DIR`/`CONFIG_FILE` as absolute `pathlib.Path`s relative to the repo root, regardless of the process's current working directory. When frozen with PyInstaller (`sys.frozen`), `BASE_DIR` instead resolves to the folder containing the `.exe` (so `config.ini`/`saved_games/` persist next to it across runs) and `ASSETS_DIR` points into the bundle (`sys._MEIPASS`) — see the "Generar un ejecutable" section in `README.md` for the build command; must be `--onedir`, not `--onefile` (the latter re-extracts to a fresh temp folder every launch, losing saves/settings). `config/settings.py` reads/writes volume settings to `config.ini` at `BASE_DIR`.

**`i18n/` — string layer (GDD §9.1)**: `i18n.t(key, /, **kwargs)` looks a key up in the active locale's catalog (`i18n/catalog_<code>.py::CATALOG`), formatting it with `kwargs`; misses fall back to the `es` catalog, then to returning the key itself (a bad `.format` degrades to the raw template). `i18n.has(key)` checks presence (used for per-status message overrides). `set_locale(code)` (unknown → `DEFAULT_LOCALE="es"`) is called once in `app.main()` from `settings.load_language()` (`config.ini` `[IDIOMA] idioma`). Scope is deliberately minimal for now — only the v0.9.0 combat/status strings are in the catalog; the bulk migration of existing hard-coded Spanish is a later phase.

**`ui/` — presentation layer**: `ui/console.py` centralizes all `colorama` usage behind `success()`/`error()`/`warning()`/`info()`/`title()` (full-line semantic messages), `say()` (plain line, status-tinted) and `colorize(text, color, bright=False)` (inline fragments, used when a single line mixes multiple colors — the dominant pattern in combat/status messages). **`colorize()` auto-tints status-effect keywords** in any text it renders via `tint_status()` (regex: `veneno`→green, `quemadura`→red, `parálisis`→yellow, `congelación`→blue, incl. word forms; `back_to` re-applies the surrounding colour after each keyword) — so status words come out the same colour everywhere without per-call effort (`colorize(..., tint=False)` and a plain `print()` opt out — used for narrative text where a word like "quemado" is just a word, e.g. the lore-note titles and the "Recorres Cabaña quemada" lines; `console.say()` always tints); a handful of raw `print()` sites (shop/inventory/forge item lines) call `tint_status()` explicitly. `STAT_COLORS` + `stat_line(text, key)` give each stat concept a fixed colour, used by `ui/formatting.py` and `Player.show_stats()`. `ui.console.ask()` wraps `input()`. Domain modules (`player.py`, `battle.py`, enemies, `inventory.py`, `save_load.py`, `menus.py`) import from `ui.console` instead of `colorama` directly, but still print directly from within domain logic — there is **no full MVC separation**; this was a deliberate choice to keep the refactor behavior-preserving rather than an architectural rewrite. `ui/menus.py` is the menu/game-loop hub (former `game_core/menu.py`), `ui/formatting.py` holds the health-bar and detailed-info renderers (former `utils/utils.py`); `print_player_enemy_info()` renders both combat sheets with per-stat colours and shows an undefeated enemy's every stat as `???` (same redaction as the HP bar), `print_bestiary_entry()` likewise.

**Menu/game loop (`ui/menus.py`)**: Everything is driven by simple numbered `input()`-based menus, no state machine framework.
- `main_menu()` → new game / load game / options / exit
- `start_new_game()` creates a `Player` with base `Stats`; `"admin"` is a **reserved name** — both it and `load_saved_game()` loop on the name prompt and refuse to proceed with that name at all unless `_check_admin_password()` passes (prompted via `getpass.getpass()`, compared as a SHA-256 hash against a constant — the real password is never stored in plaintext anywhere in the repo or the installed game); a wrong password rejects the name outright (the player must pick a different name, or retry `"admin"` with the correct password) rather than silently downgrading to a normal character. Getting it right grants a debug/cheat character (high stats, gold, all 14 enemies unlocked *and* marked defeated including the Dragón) — this is a known intentional test hook, not a bug. That same name+password combo also unlocks a "Panel de Admin" option in the "Personaje" submenu (`_admin_panel_flow` and its `_admin_*` helpers, still defined in `menus.py`) for full runtime control: set gold/level/any `Stats` field directly, full heal, mass-unlock, fight any enemy in the chain regardless of `unlocked_enemies`, or instantly get 50x of every material (which also discovers every forge recipe, for free, via `Inventory.add_item()`'s existing discovery side effect) and one of every weapon/armor any enemy can drop. The last two force `random.random()` to `0` while reading each enemy's `drop_item()` so every possible item comes out at once, and wrap the bulk `add_item()` calls in `_quiet_pickups()` to silence the per-item "Obtenido: X" print (hundreds of lines otherwise). Loading a save named "admin" still requires re-entering the password (`is_admin` isn't persisted in the save file, and is computed at the name prompt in both `start_new_game()`/`load_saved_game()`, then passed into `ui/exploration.py::zone_loop()`). The password hash comes from `config/secrets.py::ADMIN_PASSWORD_HASH` via `secret_store.get()`; if it's absent, `_check_admin_password()` returns `False` and `"admin"` stops being a special name.
- Once the `Player` exists, `start_new_game()`/`load_saved_game()` hand off to `ui/exploration.py::zone_loop()` (see below) — `menus.py` itself no longer has a per-session hub (`game_loop()` was removed in v0.12.0-b, folded into `zone_loop()`/`_character_menu()`).
- Enemy names are looked up via a hardcoded Spanish-name → class dict in `_get_enemy_instance()`.

**Zone exploration loop (`ui/exploration.py`, v0.12.0-b/c, GDD §8.1)**: replaces the old flat `game_loop` menu; `omit`ted from the coverage metric same as `ui/menus.py` (interactive glue), though its testable-enough pieces still have tests (`tests/test_exploration.py`, same convention as `test_menus.py`: monkeypatch `console.ask`). Imports from `ui.menus` only *inside* function bodies, never at module level — `menus.py` calls `zone_loop()` from `start_new_game()`/`load_saved_game()`, so a top-level `menus` import here would be a circular import.
- `zone_loop(player, unlocked_enemies, defeated_enemies, is_admin=False)` is the new per-session hub: a per-zone menu (**Explorar** / **Ir a...** / **Hablar con...** / **Viajar** / **Personaje**) instead of one flat list. Reads/writes `player.mundo["zona_actual"]` (the v0.12.0-a save-schema-v2 field) directly — no separate "current zone" parameter.
- **Explorar** (`_explore`): a weighted roll — `_EXPLORE_ENCOUNTER_CHANCE` (0.65) combat, `_EXPLORE_DISCOVERY_CHANCE` (0.15) a discovery, the remaining 0.20 "nothing of interest". A combat encounter picks an *unlocked* enemy belonging to the current zone (`_zone_candidates(zone, unlocked_enemies)`: `Zone.enemies ∩ unlocked_enemies`, in `Zone.enemies`' own declared order — which is authored low-tier-to-high-tier, same order `power_budget.py`'s tier fitting assumes; if none, e.g. a zone with no roster yet like Ciénaga de los Ahogados, falls back to any unlocked enemy at all so exploring never dead-ends — but **never** for a hub, `zone.is_hub`, see the World package section below) via `_weighted_enemy_choice` (v0.14.x, feedback: with a 10-enemy zone fully unlocked, blind uniform chance meant a post-guardian player could get sent back to the zone's weakest trash as often as anything else — now weighted `1..N` by position in that candidate list, so the most-advanced unlocked enemy is favoured without the earliest ones dropping out entirely; `random.choices(candidates, weights=range(1, len(candidates)+1), k=1)`). Goes through the same `initiate_battle(..., enemy_factory=...)` as the old "Luchar" — auto-battle chains still work identically. A discovery (`_discovery`, v0.12.0-c) is itself a roll: `_DISCOVERY_POTION_CHANCE` (0.4) a free Poción de Salud via `Inventory.add_item()`, else gold (3-10, as before) — a little variety instead of always the same reward. **In a hub** (Piedrablanca), `_zone_candidates()` always returns `[]`, so the combat branch never fires — `encounter_chance` becomes `0.0` and the discovery roll keeps its own width (`[0, _EXPLORE_DISCOVERY_CHANCE)`) instead of inheriting the slice that would've gone to combat, so finding gold/potions in the village is exactly as likely as anywhere else, just never a fight (v0.14.x, feedback del usuario: exploring the village could trigger a real battle against any unlocked enemy — a bug, not a feature, since the GDD calls Piedrablanca a "hub, no enemies"). With genuinely nothing unlocked in a non-hub zone (`not candidates and not zone.is_hub`), Explorar still reports "No hay nada que explorar todavía." as before. **A hub's discovery is capped, not infinite** (`_hub_discovery`, v0.14.x, feedback del usuario: Piedrablanca had no enemies to farm but its gold/potion discovery still rolled every time, so a player could stand still and Explorar forever for free rewards): each kind (gold, potion) is tracked with its own one-time flag in `mundo["banderas"]` (`f"hallazgo_oro_{zone.id}"` / `f"hallazgo_pocion_{zone.id}"`, same one-shot pattern as dialogue/lore flags) and appears at most once per save; the discovery roll (`_DISCOVERY_POTION_CHANCE`) only decides *which* comes first when both are still available, otherwise the still-missing one is given directly. Once both are found, hitting the discovery slice again reports "Ya has encontrado todo lo que había que encontrar en {zone.name}." instead of another reward — a real zone's `_discovery()` (used whenever `not zone.is_hub`) is unaffected and stays uncapped, since gold/potions from wilderness foraging are meant to keep coming as you explore.
- **Cazar...** (`_hunt_flow`, v0.14.x, GDD §8.1 follow-up, feedback: bring back picking a specific enemy without giving up Explorar's randomness/discovery chance): lists `_zone_candidates(zone, unlocked_enemies)` **filtered to `defeated_enemies` only**, in tier order; picking one goes straight to `initiate_battle(..., enemy_factory=...)` — no gold/potion discovery roll, that stays Explorar's incentive. The "frontier" enemy (the newest unlock, not yet beaten even once) is deliberately excluded (playtest fix — an earlier version listed it too, which let a player see/fight it from a menu meant for farming already-known enemies before ever meeting it through Explorar); with nothing defeated yet in the zone, it reports there's nothing to hunt instead of showing an empty-looking list. In a hub, it short-circuits before even checking `defeated_enemies` with a distinct "zona segura" message — there's never anything to hunt there, no matter the game state. Sits as menu option 2 (`zone_loop`'s labels are now `Explorar, Cazar..., Ir a..., Hablar con..., Viajar, Personaje` — 6 options, shifting every index after it by one from v0.12.0-b/c's original 5).
- **Ir a `<sub-lugar>`** (`_sublocation_flow`): lists `Zone.sub_locations`; a sub-location can be wired to a real service via `_ZONE_SERVICES` (a `dict[(zone_id, sub_location_name), Callable[[Player], None]]`), otherwise it prints a generic "nothing to do here yet" stub line. Since v0.12.0-c, Piedrablanca's 3 of its 4 sub-locations are wired: `("piedrablanca", "Mercado")` → `_open_shop` (opens `Shop`), `("piedrablanca", "Herrería")` → `_open_forge` (opens `Forge`), `("piedrablanca", "Taberna")` → `_rest_flow`. "Refugio" and every sub-location in every other zone are still stubs — NPCs/services/quest turn-ins beyond these three are GDD §8.2/§8.3, planned for v0.13.0. (Tests that need to intercept a service monkeypatch the `_ZONE_SERVICES` dict entry with `monkeypatch.setitem`, not the function name directly — `_sublocation_flow` looks the handler up from the dict, which captured the function object at module-load time, so rebinding `exploration._open_shop` after the fact wouldn't be seen.)
- **Hablar con...** (`_talk_flow`, v0.13.0-a): lists `world.map.npcs_in_zone(zone.id)` ("No hay nadie con quien hablar aquí." if none) and calls `npc.talk(player, show=, pick=, notify=)` with console-backed callbacks; `_pick_reply(options)` prints the numbered replies and re-asks until valid. After `npc.talk()` returns (the NPC's last line — a closing reply or an idle line) it waits for a "Presiona Enter para continuar..." so the text can be read before the zone menu redraws (playtest fix). All dialogue logic lives in `world/npc.py` (below) — this function only prints and asks.
- **Lore notes and the Diario** (v0.13.0-c, GDD §2): `world/lore.py` defines `LoreNote(id, zone_id, sub_location, title, text)` plus pure helpers `add_note(player, note) -> bool` (True the first time; appends the id to `mundo["diario"]`, a list in discovery order), `has_note` and `found_notes(player, catalog)` (ignores ids missing from the catalog, so a note renamed later can't break an old save). Each `world/data/<zone>.py` may expose `LORE = (LoreNote(...), ...)`; `world/map.py` aggregates them into `LORE_NOTES` and `note_for_sub_location(zone_id, place)`. **Notes come only from sub-locations**: in `_sublocation_flow`, after the `_ZONE_SERVICES` check, a place without a service shows its note on the first visit (`_show_note`, followed by a "Presiona Enter para continuar..." pause — playtest fix) and "Ya has leído todo lo que había que leer aquí" afterwards; a place with no note falls back to the old stub line. 13 notes exist (Refugio + 2 per zone from Los Yermos to the Ciudadela; El Corazón de la Brecha has none). `tests/test_lore.py` enforces that every sub-location without a service has exactly one note and that services (Mercado/Herrería/Taberna) have none. `_diary_flow` (Personaje → "Diario (found/total)", placed right after Bestiario) lists found notes grouped by zone in `ZONE_ORDER` order, numbered continuously, and re-reads the chosen one. Adding the Diario shifted the Personaje indices (Volver a la zona = 10, Volver al Menú Principal = 11, Salir = 12; with Panel de Admin the last two move up by one) — a wrong index in a `console.ask` test loops forever rather than failing.
- **Rest** (`_rest_flow`, v0.12.0-c, GDD §7.4): at Piedrablanca's Taberna. Cost is `_REST_COST_PER_LEVEL` (10, explicitly provisional — GDD listed "the gold-per-level formula" as an open question) `× player.level`, confirmed with a y/n prompt; on accept, fully heals and does `player.status_effects.clear()`. Refuses (with a message, no gold spent) if the player can't afford it; short-circuits with "you don't need to rest" if already at full HP with no status effects, before even showing the cost.
- **Viajar** (`_travel_flow`): fast-travel (instant, free) to any zone already in `player.mundo["zonas_visitadas"]`, plus "`<zona>` (frontera)" for `world.map.next_zone(zona_actual)` when `world.map.is_zone_reachable()` says so and it isn't visited yet. Travelling updates both `zona_actual` and appends to `zonas_visitadas` (no duplicates). A zone with no roster is always "reachable" (nothing to block it) per `is_zone_reachable()`'s rule from v0.12.0-a; walking to it only ever advances one hop (to the *immediate* next zone in `ZONE_ORDER`), it doesn't skip ahead past a not-yet-open zone.
- **Personaje** (`_character_menu`): everything else that used to hang off `game_loop` directly — Inventario, Estadísticas, Habilidades, Bestiario, Diario (v0.13.0-c), Equipar Arma/Armadura, Opciones, Guardar Partida, Volver a la zona, Volver al Menú Principal, Salir del Juego, plus Panel de Admin when `is_admin`. Tienda/Herrería *no longer* live here (v0.12.0-c moved them into Piedrablanca's "Ir a..." — see above); everything else stayed. Returns `"volver_menu"` (a sentinel string, not `None`) when the player picks "Volver al Menú Principal", which `zone_loop()` checks to `break` out of its own loop; any other selection returns `None` and stays in the character menu (or, for "Volver a la zona", exits back up to the zone menu). "Salir del Juego" calls `sys.exit()` directly, same as before.

**Combat (`combat/battle.py`)**: `initiate_battle()` is the turn loop entry point.
- `ENEMY_PROGRESSION` dict defines the fixed unlock chain, 20 enemies long since v0.14.0-c (was 14), with newer enemies inserted at the tier matching their relative power rather than appended at the end: Goblin → Rata Gigante → Goblin Montaraz → Huargo → Chamán Goblin → Esqueleto → Bandido → Salteador → Ogro del Yermo → El Carnicero (guardián, opens the Bosque) → Orco → Espíritu Vengativo → Troll → Gárgola → Gólem de Piedra → Mago → Nigromante → Ángel Caído → Demonio → Dragón (final boss, maps to `None`). Beating a new enemy for the first time unlocks the next one and adds it to `unlocked_enemies`.
- **ATB turn system**: each combatant accumulates a `gauge` every tick at a rate proportional to `Player.get_total_speed()` / `enemy.stats.speed`; whoever reaches `ATB_THRESHOLD` (100) first acts, with the overflow carried over (not reset to 0) — this is a Final-Fantasy-X-style "active time battle" where the faster combatant can act multiple times before the slower one gets a single turn, not just a simple alternating order. When both gauges are ready in the same tick, the player's turn (and a flee attempt) always resolves first, so a faster enemy can never interrupt a flee. Fleeing succeeds with probability `min(1.0, player_speed / enemy_speed)`. The pre-battle "⚡ {name} tiene la iniciativa" message (v0.14.0-c playtest fix) mirrors this tie-break rule instead of naively comparing raw speed: `ticks = ceil(ATB_THRESHOLD / speed)` for each side, and the player is announced whenever `ticks_jugador <= ticks_enemigo` — with close speeds (e.g. 10 vs 11) both sides often reach the threshold in the *same* tick, so a naive "higher speed wins" comparison could announce the enemy even though the player's turn resolves first per the rule above; the message now always names whoever the battle loop will actually let act first. It no longer prints the raw speed numbers either (`⚡ {name} tiene la iniciativa.`, no parenthetical) — before the enemy is defeated at least once, its speed is a stat the Bestiary still redacts as `???`, so showing it here leaked hidden information; the message now only answers "who goes first".
- Player stat changes from potions during battle are snapshotted at battle start and restored via `_restore_player()` at battle end (so buffs don't persist outside combat). Post-battle healing (50% of missing HP) also runs there, except after a defeat (already fully healed by `_handle_defeat()`); on a successful flee, `_restore_player(..., max_recovery=...)` caps that healing to only the HP lost *during that specific battle* (tracked via `health_before_battle`, snapshotted at the very start of `initiate_battle()`) — fleeing isn't a win, so it shouldn't also heal damage carried over from earlier fights. A victory triggers an explicit "Presiona Enter para continuar..." pause (`player_won` flag) after all the loot/XP/heal text prints, so the game-loop menu doesn't redraw over it before the player can read what they got.
- **`_handle_victory` screen** (v0.14.x, feedback del usuario): gold and XP lines now show running totals, not just the delta — `💰 Oro obtenido: {gold} (Total: {player.inventory.gold})` and `✨ XP obtenida: +{xp_gained}  (Nivel {player.level}: {player.experience}/{player.required_xp()})` (the level/XP values are read *after* `gain_experience()`, so a level-up already shows the new level and its own threshold). `Player.gain_experience()` no longer prints its own "Has obtenido X XP." — that line predated this and would just duplicate the new one (its only caller is `_handle_victory`). Unlocking the next enemy in `ENEMY_PROGRESSION` still happens exactly as before (appended to `unlocked_enemies`), but the `"✨ ¡NUEVO ENEMIGO DESBLOQUEADO: {name}!"` announcement was removed — the player should discover who it is by actually exploring, not read it off the victory screen.
- **Hit resolution**: `characters/stats.py::resolve_hit(attacker_precision, defender_evasion)` is a shared 100%-base-chance roll (against 0 evasion the attacker always hits; each point of the defender's evasion above the attacker's precision subtracts 1%, floor 5%/ceiling 100%) used by both `combat/battle.py::_execute_turn` (player's standard attack) and `Enemy.perform_turn()`'s default attack, plus most enemy special attacks individually. A handful of unconditional-hit special attacks exist on purpose (e.g. the Gólem's "Terremoto" — thematically an earthquake you can't dodge). `BASE_HIT_CHANCE` used to be 90 (so even 0-evasion targets had a baseline miss chance); changed to 100 on request so evasion is the only source of dodging — this is a global change, and the whole 14-enemy chain was originally calibrated assuming the 90% base (see `TODO.md`'s "Sistema de acierto" section — only the Goblin has been re-verified against the new formula so far).
- **Critical hits are not player-only**: every enemy has its own `crit_chance`/`crit_damage` on `Stats` (rolled the same way as the player's, via `random.random() < crit_chance`, multiplying damage by `crit_damage` on a hit) — `combat/battle.py::_execute_turn` and `Enemy.perform_turn()` both branch on whether the combatant is a `Player` (uses `get_total_crit_*()`, summing equipment) or an enemy (uses the bare `Stats` value, since enemies have no equipment).
- **Skill/crit damage uses the max of the attack range, not another roll of the dice (v0.14.0-c playtest fix)**: a normal attack still calls `get_attack_damage()` (`random.randint(min_atk, max_atk)`) as always, but the base becomes deterministic — the *ceiling* of the attack range — whenever the hit is a crit, or (player-only) a damage skill. The multiplier (`damage_mult` for a skill, `crit_damage` for a crit) still applies on top of that ceiling exactly as before — only the *base* changed from "a random roll" to "always the best case". Fixes the complaint that a 40%-boosted skill or a lucky crit could roll below a normal attack's own lucky high roll, since previously both were multiplying the *same* wide, proportionally-swingy `min_atk`-`max_atk` roll.
  - **Player side** (`combat/battle.py::_execute_turn`): takes `get_attack_range()[1]` (or `get_magic_attack_range()[1]` for an Arcanista) whenever `is_skill_attack = bool(skill_params)` (every utility skill like Escudo de Maná returns early in `_execute_skill` before reaching this code, so any non-empty `p` here is a damage skill) or `is_crit` — both computed *before* the damage line so the choice can be made up front. `tests/test_battle.py::test_execute_turn_crit_uses_max_attack_not_the_dice_roll` / `..._skill_damage_uses_max_attack_not_the_dice_roll` / `..._normal_attack_still_rolls_the_dice`.
  - **Enemy side** (extended to enemies on request, accepting that it shifts their average damage above what the power-budget tool assumed when the roster was tuned — not rebalanced back in response): `Enemy.get_max_attack_damage()` (`enemy_base.py`, mirrors `get_attack_damage()` including the `quemado`/`combustión` physical-damage halving) is the shared helper. Every enemy-side crit roll across the roster was updated to check `is_crit` *before* picking the damage base (`get_max_attack_damage()` if crit, `get_attack_damage()` otherwise) instead of multiplying whatever `get_attack_damage()` already returned: the shared default `Enemy.perform_turn()`, Orco's furia branch, and every enemy with its own attack method that rolls a crit (Ángel Caído, Chamán Goblin, Demonio, Dragón, El Carnicero, Goblin Montaraz, Nigromante, Rata Gigante, and each of the Mago's 4 spells — there the deterministic max only replaces the base `atk_base` roll, the spell's own additive bonus roll, e.g. `random.randint(15, 25)` for Bola de Fuego, is untouched). Attacks that never rolled a crit to begin with (Gárgola's charge, Gólem's earthquake, Ogro del Yermo's crushing blow, Salteador's second strike — each a deterministic fixed-multiplier "special hit") were **not** given a new crit roll; only existing crit rolls were changed to use the deterministic base. `tests/test_battle.py::test_enemy_default_perform_turn_applies_crit_multiplier` covers the shared default with the same low-`randint` trick as the player tests.
- **Physical vs. magical damage and penetration**: `Player.take_damage(amount, is_fire=False, is_magical=False, armor_penetration=0, magic_penetration=0, element=None)` and `Enemy.take_damage(...)` (mirrored signature, no `element` param — see below) pick `armor`/`magic_resist` as the `mitigation` value based on `is_magical`, then subtract the attacker's matching penetration stat from it. Several enemies now deal magical damage beyond the Mago (e.g. Nigromante's dark bolt, Ángel Caído's holy strike/Juicio Divino, Demonio's summoned lesser demon) — check an enemy's `perform_turn()`/attack helpers rather than assuming only the Mago passes `is_magical=True`. `is_fire` is orthogonal to `is_magical`: it only controls whether the "congelado" status gets melted, unrelated to mitigation. **`is_magical` is decided by the element, not the class (v0.11.0-b fix)**: `combat/battle.py::_execute_turn` used to only check `attacker.is_magical_attacker()` (Arcanista) or a skill's `magical` flag, so a Guerrero/Pícaro/Aventurero wielding a sagrado/oscuridad/arcano weapon was still armour-mitigated — now `is_magical_element(element)` (`combat/elements.py`) also triggers it, matching the GDD rule that physical/magical is a property of the element itself. `element` on `Player.take_damage` (added in v0.11.0-b, alongside `Enemy.take_damage`'s pre-existing one) feeds `Player.get_total_resist(element)` — see the Items bullet below — and is tagged on every enemy attack that's clearly elemental (Mago's 4 spells, Nigromante's dark bolt → oscuridad, Ángel Caído's holy strike/Juicio Divino → sagrado, Demonio's claw/summoned-demon → fuego per its own "daño ígneo" flavour text, Dragón's fire breath → fuego); enemies with no elemental attack (most of the roster) don't pass it and default to `None`.
- **Mitigation is multiplicative** (`characters/stats.py::apply_mitigation(amount, mitigation)`): `reduced = amount * DEFENSE_SOFTENING / (mitigation + DEFENSE_SOFTENING)` with `DEFENSE_SOFTENING = 20`, `mitigation` floored at 0, result `max(1, round(...))` — a Raid-style diminishing-returns curve (~50% reduction at mitigation 20), never full absorption. This **replaced** the old subtractive `damage - armor`; the 14-enemy chain was calibrated against the old formula and still needs a rebalance pass (`TODO.md`).
- **Elemental affinity (`combat/elements.py`)**: `affinity_multiplier(elements, *, weaknesses, resistances, immune_elements) -> float` — the current model, and (since v0.11.0-a) the **only** one: every one of the 20 enemies declares real `WEAKNESSES` / `RESISTANCES` / `IMMUNE_ELEMENTS` / `IMMUNE_STATUSES` (`frozenset`s on the class; empty = neutral), the legacy per-class `ELEMENTAL_WEAKNESSES: dict[str, float]` fallback has been removed entirely. Weakness ×1.5 (×2.0 if two of the attack's elements are weak), resistance ×0.5 (×0.25 if two, and it also halves that element's on-hit status chance/duration — `Enemy.resists_element()`), immune element → ×0 and no status. **Rule enforced in the data (not the affinity function itself):** if an enemy is `IMMUNE_ELEMENTS` to an element, it is also `IMMUNE_STATUSES` to that element's `ELEMENT_STATUS` — required because at least one status application path (the Pícaro's Veneno de Contacto passive in `_execute_turn`) calls `enemy.apply_status(...)` directly without checking `affinity_for()` first, so without the explicit `IMMUNE_STATUSES` entry an "immune to the element" enemy could still be inflicted with its status through that path. The reverse isn't required: `IMMUNE_STATUSES` alone (e.g. Esqueleto is immune to the `veneno`/`sangrado` *statuses* but only *resists* the `veneno` element, so poison weapons still deal reduced damage) doesn't imply `IMMUNE_ELEMENTS`. 7 elements total, split `PHYSICAL_ELEMENTS` (fuego/veneno/rayo/hielo) vs `MAGICAL_ELEMENTS` (sagrado/oscuridad/arcano). `ELEMENT_STATUS` maps each element to the status it can inflict. Current affinities: Goblin/Huargo neutral; Esqueleto weak sagrado, resists veneno, immune to veneno/sangrado statuses; Bandido weak veneno; Orco resists veneno; Espíritu Vengativo weak sagrado, immune veneno (element+status) and also immune to the `sangrado` status alone (incorporeal, no body to bleed even though bleed isn't tied to an element); Troll weak fuego; Gárgola weak arcano, immune veneno (element+status); Gólem weak hielo, immune rayo (element+status, i.e. can't be `paralizado`); Mago resists arcano (its physical frailty is expressed via low `armor`, not an elemental weakness); Nigromante weak sagrado, immune oscuridad (element+status); Ángel Caído weak oscuridad, resists sagrado; Demonio weak sagrado, resists oscuridad (deliberately only *resists*, not immune, to stay distinct from the Nigromante); Dragón weak hielo, immune fuego (element+status, thematically the "Dragón de Ceniza"); the 6 Los Yermos additions (v0.14.0-c) are lighter on affinities — Rata Gigante/Goblin Montaraz/Salteador neutral aside from a fire weakness on the first two, Chamán Goblin weak sagrado/resists oscuridad, Ogro del Yermo weak fuego/immune paralizado, El Carnicero weak sagrado/resists veneno.
- **Elemental reactions** (`combat/elements.py`, v0.11.0-c): two special-cased interactions between elements, layered on top of the affinity model above. **Shatter** (`is_shatter_hit()`): a `rayo`-element hit against a target that currently has `congelado` removes the freeze instantly and multiplies the damage by `SHATTER_DAMAGE_MULT` (1.5×) instead of the normal on-hit rayo status attempt — both `Player.take_damage()` and `Enemy.take_damage()` set an instance flag (`just_shattered`, reset every call) so the *separate* call that would otherwise try to apply `paralizado` afterwards (`combat/battle.py::_try_inflict_weapon_status` for a player's rayo weapon, `Mago._cast_thunder` for the enemy side) can check it and skip — this mirrors the existing `took_physical_hit` flag pattern for Represalia. All 4 physical elements have a player-obtainable weapon (Garra de Tormenta = rayo from Gárgola, Cetro de Escarcha = hielo from Nigromante, plus the fuego/veneno ones), so shatter is reachable from both directions in normal play, not just from Mago's spells. **Combustion** (`resolve_status_reaction()` + `is_status_blocked_by_combustion()`): applying `quemado` while `veneno` is already active (or the reverse) merges them into a single `combustion` status instead of letting them coexist; once `combustion` is active, a further attempt to apply either half is a no-op — blocked before touching `status_effects`, so it doesn't refresh the duration or re-trigger the fusion message — handled generically inside `apply_status()` on both `Player` and `Enemy`, so every existing call site (weapon procs, Mago's fire/poison spells, Veneno de Contacto, Dragón/Orco/Demonio's fire attacks) gets the merge for free with no per-caller change. `combustion` deals more damage per turn than `quemado` or `veneno` alone (`max_health // 6`, vs. `// 16` and `// 8` respectively), halves physical attack same as `quemado` (`get_attack_damage()`/`get_attack_range()` check for either name), stays in `AntidotePotion.CURABLE`, and respects `Enemy.IMMUNE_STATUSES` (an enemy immune to `veneno`'s status can never hold both halves at once, so the merge path is naturally unreachable for it — no separate `combustion` immunity is needed in the roster today, though the check exists defensively). **Message ordering** (playtest fix): `apply_status()` never prints the fusion message itself — it only sets `self.last_status_reaction`; the caller prints its own "ha sido quemado/envenenado" line first, *then* calls `pop_status_reaction_message()` (returns the pre-colorized fusion line and clears the flag, or `None`) so the fusion note always reads *after* the status that triggered it, never before. Every `quemado`/`veneno`-applying call site follows this two-line pattern (`combat/battle.py`'s Veneno de Contacto passive and `_try_inflict_weapon_status`, `Mago._cast_fireball`/`_cast_poison`, `Dragon._fire_breath`).
- Status effects live as dicts (`{"name", "duration", "power", "fresh"}`) in `player.status_effects` / `enemy.status_effects`. **Both** `Player` and `Enemy` now process them symmetrically: `on_turn_start()` (returns `can_act: bool` — DoT for quemado/veneno, skip-turn rolls for congelado/paralizado; a `fresh` effect is guaranteed to skip its first turn, then 20%/50% thaw/act rolls), `on_turn_end()` (regen), `decay_status_effects()` (duration tick + fade message), `apply_status(name, duration, power=0) -> bool` (False if immune; refreshes to `max(duration)`). `Enemy` also has `announce()` / `pop_announcements()` so its status/AI messages print *after* the turn's HP-bar summary. `quemado` is physical-only (no longer melted by any magical hit). `fractura_magica` zeroes the target's `magic_resist` for its duration (replaced the scrapped `silenciado`). `sangrado` (bleed) is a physical DoT (`max_health // 12`/turn) applied by the Pícaro's Golpe Bajo skill; `aturdido` (stun, from the Guerrero's Embate) skips the turn while it lasts with no escape roll — a distinct status from `paralizado` so its messaging/colour differ. Each status word (plus `contraataque`/`represalia`) has its own colour in `ui/console.py::_STATUS_PATTERNS` (regex-based auto-tinting via `console.tint_status`, which `colorize` also applies); skill descriptions are printed through it. Player-only enemy debuffs still exist, each read back by a `get_total_*()`: `desarmado` (Bandido), `maldicion` (Espíritu Vengativo), `confusion` (Demonio).
- **Weapon-inflicted status** (`combat/battle.py::_try_inflict_weapon_status`): after the player's damage line, a weapon with an `element` (or an explicit `inflicts` dict on `Weapon`) rolls to apply the element's status on the enemy. Skipped entirely if the player is `desarmado` or the enemy is immune to the element; chance ×0.5 and duration halved if the enemy merely resists it.
- **Affinity feedback in `_execute_turn`** (v0.11.0-a wording pass): `combat.resisted_hit` reads "{name} es resistente al {element}." (not "resiste el {element}.") so it reads as reduced damage, distinct from "es inmune al {element}: el ataque no le hace nada." (`combat.immune_hit`). When the hit is `is_immune_hit`, the generic "{defender} ha bloqueado el ataque." zero-damage line is skipped — the immune message already explains the 0 damage, so both together were redundant/confusing (that generic line still fires for any other future zero-damage cause). The Pícaro's Veneno de Contacto passive also announces immunity explicitly ("{defender} es inmune al veneno.") when its chance-roll succeeds but `apply_status` fails — otherwise a player fighting an immune enemy for the first time can't tell if the passive is even proccing.
- **"Defender" action** (`_player_menu` returns `"defender"`): spends the turn and sets `Player.defending = True`, which halves the final damage in `Player.take_damage()` (and, since it bypasses `take_damage`, in the Orc's enraged blow). The flag is cleared at the top of the next `_run_player_turn()` and by `_restore_player()`, so it lasts only until the player's next turn. Not persisted.
- **`_player_menu`'s option order** (v0.11.0-c): Atacar, Habilidades (only if the player has an equipped active skill), Defender, Objetos, Huir, Info, Auto-Batalla, Auto-Batalla Turbo — the two action choices and the defensive one come first, the utility ones after. The `options: list[tuple[str, str]]` is built fresh each loop and rendered by enumeration, so reordering is just reordering that construction; nothing downstream depends on a fixed index.
- `initiate_battle()` prints `print_player_enemy_info()` (both sheets) once right after any ambush and before the turn loop, so the player always sees the matchup regardless of who acts first.
- The Goblin (only) doesn't run its pre-battle ambush until it's in `defeated_enemies` — `check_ambush(self, player, defeated_enemies=None)`, mirrored on the Bandido which ignores the new arg (it ambushes from the first encounter).
- "Auto-battle" mode (only unlockable against previously-defeated enemies) polls the keyboard each turn to let the player cancel by pressing `q`, via `combat/battle.py::check_for_interrupt()` → `ui/keyboard.py::key_pressed()` (non-blocking, cross-platform: `msvcrt` on Windows, `select`+`termios` on POSIX, `None` when stdin isn't an interactive terminal). The terminal-touching branches carry `# pragma: no cover`. `is_auto` is a tri-state: `False`, `"auto"` (normal, keeps the ~1s turn pauses and the victory "Presiona Enter"), or `"turbo"` (farming mode: every `time.sleep` skipped, no "esperando…" line, no victory pause — but the per-turn health bars and announcements still print, so the fight stays legible). `_run_one_battle` prints who has the initiative (higher speed; ties → player) and heads every action with `_turn_header(turn_no, name, extra)` — a single global action counter, so a faster combatant visibly acts more often; the player's header carries the class name (`Player.class_name`). `_run_enemy_turn` sleeps ~1s at both ends (unless turbo) so the enemy's damage is readable before the menu. `_player_menu`'s options line (`_turn_header` prints its own leading blank line to separate turns, but the menu itself no longer does — v0.11.0-a fix) sits directly under the turn header or the "Eres más rápido" notice, matching the tight enemy-turn layout instead of leaving a stray blank line above the numbered options. **Consecutive-turn notice, both directions** (v0.14.x playtest fix): `_run_one_battle` tracks `enemy_acted`/`player_acted` across the ATB loop and passes `repeated=` into `_run_player_turn`/`_run_enemy_turn` whenever a combatant is about to act again without the other side having had a turn in between (a faster combatant crossing the ATB threshold more than once before the slower one crosses it even once). The player's side already printed "⏩ Eres más rápido..."; the enemy side previously printed nothing, so a fast enemy silently taking two turns in a row read as a bug rather than the ATB system working as designed — `_run_enemy_turn` now prints its own mirror line ("⏩ {enemy} es más rápido: actúa de nuevo antes que tú.") right after its turn header under the same condition. **Auto-battle chains**: `initiate_battle(..., enemy_factory=)` is a loop over `_run_one_battle` (the actual single-fight body). When the player turns on auto/turbo against an already-defeated enemy, `_run_player_turn` calls `battle._ask_chain_count()` (≤ `_MAX_CHAIN_BATTLES` = 20) and records the choice + current mode in a shared `chain` dict; `initiate_battle` then spawns `enemy_factory()` for each subsequent fight. The mode is re-read every time the player picks auto/turbo, so you can switch Auto↔Turbo mid-chain (pressing `q` drops to the manual menu without ending the chain). `initiate_battle` returns the last fight's outcome (`"victory"` / `"defeat"` / `"fled"` / `"cancelled"` — `"cancelled"` = pressed `q` and finished manually without re-enabling auto); the chain stops on anything but `"victory"`. One post-battle pause at the very end (for a chain, always — after `_print_chain_loot` diffs gold/XP/levels/items against a start-of-chain snapshot; for a single fight, skipped after a clean turbo win and after a defeat, which already paused — `_handle_defeat(pause=...)` is told not to pause mid-chain). `enemy_factory` is `None` for callers that can't chain (tests) → single fight.
- On defeat, the player loses 1/3 of gold and is fully healed rather than getting a game over.

**Characters (`characters/`)**:
- `base.py`: abstract `Character` (name, stats, status_effects) — note `Player` and `Enemy` do NOT actually share this base in practice; `Enemy` (`characters/enemies/enemy_base.py`) is defined independently with its own `take_damage`/`is_alive`. Don't assume polymorphism between `Player` and `Enemy` beyond duck-typing (`is_alive()`, `take_damage()`, `get_attack_damage()`).
- `stats.py`: `Stats` encapsulates HP/attack range/`armor` (physical mitigation)/`magic_resist` (magical mitigation)/`crit_chance`/`crit_damage` (base 0.0 / 1.5x)/`speed` (feeds the ATB gauge, default 10)/`precision`/`evasion` (feed `resolve_hit()`)/`armor_penetration`/`magic_penetration` (reduce the *target's* mitigation, not a defensive stat)/`regen` (passive HP/turn); `health` is a property clamped to `[0, max_health]`. Also hosts the shared `resolve_hit()` function and its constants (`BASE_HIT_CHANCE`/`MIN_HIT_CHANCE`/`MAX_HIT_CHANCE`) — see the Combat section above.
- `classes.py`: `CharClass` enum (`vagabundo` / `guerrero` / `picaro` / `arcanista` — the `vagabundo` value is the balanced class, whose **display name is "Aventurero"**; the enum value stays `vagabundo` for save compatibility) + `ClassProfile` dataclass (starting-stat deltas, per-level growth multipliers, `is_magical_attacker`, starting `magic_power`). `starting_stats(cls)` builds a new character's `Stats` from the Vagabundo baseline + the class deltas; `get_profile()` resolves any unknown value back to Vagabundo. Numbers are **provisional** (GDD §6.2.1, rebalanced in v0.14). `Player(name, stats, char_class=...)` defaults to Vagabundo — which is byte-for-byte the old character (all deltas 0, all mults 1.0), so every existing `Player(...)` call and old save is unchanged. The class is chosen in `ui/menus.py::_choose_class()` at creation and persisted as `clase` in the save.
- `skills.py`: `Skill` dataclass (`id`, `name`, `char_class`, `kind` = passive/active, `milestone`, `description`, `cooldown`, `params` dict), `CATALOG` keyed by id, `pool_for(cls)` / `known_skills(cls, level)` (`MILESTONE_LEVEL` maps milestone→provisional unlock level; M1=1, M2=4). Effects are param-driven, read at their call sites — **passives**: `Player.has_passive(id)` at `get_total_evasion` (`params["evasion"]`), `take_damage` (`params["phys_dmg_taken_mult"]`), `_handle_victory` (`params["heal_on_kill_pct"]`), and `_prompt_battle_element` (`params["choose_element"]` → Sintonía sets `player.battle_element` for the fight, cleared by `_restore_player`); **actives**: `combat/battle.py::_execute_skill` → `_execute_turn(..., skill_params=)` honours `guaranteed_hit` / `damage_mult` / `force_crit` / `magical` / `pierce_magic_resist` / `stun_chance` / `bleed_turns`. Cooldowns live in a per-battle `dict` threaded through `_run_player_turn`; `player.equipped_skills` (≤ `MAX_EQUIPPED_ACTIVES` = 4) is the equipped-actives list, persisted, `sanitize_equipped_skills()` / `autoequip_skills()` fix it on load. "Habilidades" is both a `game_loop` menu (`ui/menus.py::_skills_flow`) and a combat action. M1 + M2 shipped (v0.10.0-b/-c); M3+ later. M2 adds hooks: `Player._low_hp_defense_mult()` (Aguante, applied in `get_total_armor`/`get_total_magic_resist`), `Player.mana_shield` (Escudo de Maná — a `utility` active that doesn't attack; `take_damage` absorbs the next damaging hit and clears it), `Player.took_physical_hit` + `battle._try_represalia` (Guerrero counter after the enemy turn), and an `on_hit_poison_chance` check in `_execute_turn` (Veneno de Contacto). `Player.passive_param(id, key, default)` reads a learned passive's param. Numbers provisional (`TODO.md`).
- `player.py`: combat math (attack range including equipped weapon bonus), status effect processing, leveling. The Arcanista's standard attack is magical: `is_magical_attacker()` (from the class profile) makes `get_attack_damage()` roll `get_magic_attack_range()` (derived from `Stats.magic_power`, not the weapon; burn — physical-only — doesn't reduce it) and makes `combat/battle.py::_execute_turn` pass `is_magical=True` + `magic_penetration` to `Enemy.take_damage` with element defaulting to `arcano`. `magic_power` grows every level only for a class with a non-zero `magic_power_growth_rate`; `_level_up()` also applies the profile's `armor_growth_mult` / `speed_growth_mult` on top of the base `_*_GROWTH_RATE`. `player.equipped_skills` (list of active-skill ids, ≤4) is persisted (`habilidades_equipadas`) but unused until the skill system (v0.10.0-b). `gain_experience()` never resets `self.experience` — it's a cumulative total compared against `required_xp()` on every call (`while self.experience >= self.required_xp(): self._level_up()`), not a per-level cost that gets subtracted. This means `required_xp()`'s output **must** be non-decreasing as level increases, or a single small XP gain can trigger an unintended double level-up (this actually happened during tuning — see below). `Player._required_xp_for_level(level)` (a `@staticmethod`) holds the actual curve; `required_xp()` calls it for the current level and clamps the result to be `>=` the previous level's value via `max()`, guaranteeing monotonicity regardless of what the damping parameters below do. The curve itself: level 1→2 is hardcoded to 8 XP — the minimum a single Goblin kill can grant (`gold_min=4 * 2`), so the very first victory of the game always levels up. Levels 2-9 apply a `damping` multiplier on top of the level≥2 scaling formula — starts at 50% of the normal cost at level 2 (a deliberately calculated midpoint: `98.68 * 0.5 ≈ 49`, between the cheap level 1 and the original undamped level-2 cost of 98) and closes linearly to 100% by level 10 — so there's no jarring cliff right after the cheap level 1 (the original, undamped formula jumped from 8 XP to 375 XP between levels 1→2 and 2→3); level 10+ matches the original, undamped formula exactly, since that's the pacing the late-chain enemies were balanced against. Growth is deterministic but non-uniform per stat via `_growth_gain` (a Pokémon-style `floor(rate * level) - floor(rate * (level-1))` formula, so e.g. a 1.4/level rate produces the fixed sequence 1,2,1,2,1...) — `armor`/`speed`/`min_atk`/`max_atk` grow every level at their own rates, `magic_resist` only every *even* level (deliberate balance against the Mago, not generic growth), and crit/regen/penetration are excluded from leveling on purpose — they stay fixed at their starting value (crit_chance starts at 15% for a new character, set in `ui/menus.py::start_new_game`; regen/penetration start at 0) and only move via equipment.
- **Equipment slots**: `Player.equipped_weapon` (single item, unchanged) + `Player.equipped_armor` — a `dict[str, Item | None]` keyed by `items.equipment.ARMOR_SLOTS` (`casco`, `hombreras`, `peto`, `brazales`, `guantes`, `cinturon`, `perneras`, `botas`, `anillo1`, `anillo2`, `amuleto`; 11 slots, Diablo-3-style). Every `get_total_*()` method on `Player` (`get_total_armor`, `get_total_magic_resist`, `get_total_crit_chance`, `get_total_crit_damage`, `get_total_speed`, `get_total_regen`, `get_total_precision`, `get_total_evasion`, and the armor-sourced part of `get_attack_range()`) sums the base `Stats`/weapon value with the matching bonus from **every** equipped armor piece that has one — most pieces only set a handful of the 12 possible bonus fields on `Armor` (`defense`, `max_health`, `magic_resist`, `crit_chance`, `crit_damage`, `damage`, `element`, `regen`, `speed`, `precision`, `evasion`, `resist`), the rest default to 0/`None`/`{}` and contribute nothing. `get_total_armor_penetration()`/`get_total_magic_penetration()` still only return the base `Stats` value — no `Armor` field grants those yet. `get_equipped_element()` checks the weapon first, then falls back to whatever's in the `"brazales"` slot. Max-health bonuses are the one exception to "sum on demand": since `Stats.health`'s setter clamps against `Stats.max_health` and `Stats` has no visibility into equipment, `Armor.use()` directly mutates `player.stats.max_health` (reversing the previous occupant of that slot first, then re-triggering the health setter's clamp via `player.stats.health = player.stats.health`) rather than computing a "total max health" dynamically like the other stats.
- **Every armor slot has a mandatory "base stat"** that every drop for that slot guarantees, on top of 0-3 extra secondary stats (1-4 total, never more): casco→`max_health`, peto→`defense`, hombreras→`precision`, brazales→`crit_chance`, guantes→`crit_damage`, cinturon→`defense` (same field as peto, just flavored as a belt), perneras→`evasion`, botas→`speed`, anillo→`crit_damage`, amuleto→`magic_resist` (`tests/test_armor_progression.py::BASE_STAT_BY_SLOT` is the source of truth). Within a slot, the base stat's magnitude generally doesn't decrease as you move along the 20-enemy chain (mirroring the weapon-damage rule below) — `test_base_stat_does_not_decrease_within_the_same_slot_along_the_chain` enforces this, except two deliberate thematic exceptions tracked in that test's `KNOWN_EXCEPTIONS`: the Mago's peto (a robe shouldn't out-armor a golem's plate — compensated with `magic_resist` instead) and the Gólem's boots (kept deliberately slow — 1 speed, not 0 — to preserve their "trade speed for tankiness" identity against the Huargo's). Stat *count* also loosely trends up along the chain (early-game pieces stay closer to 1-2 stats, late-game ones can reach 3-4) but this isn't a hard rule, unlike the base-stat-present and 1-4-range checks which are.
- **Ring slots are a category, not a 1:1 slot**: unlike the other 9 slots, `anillo1`/`anillo2` both accept any `Armor` whose `.slot == "anillo"` (a marker, not a real key of `equipped_armor`) — `items/equipment.py::slot_accepts(filter_slot, item_slot)` encodes this (rings: category match; everything else: exact match), and both `Inventory.show_inventory()`/`_handle_selection()` filter through it instead of `==`. Because a ring doesn't know by itself which of the two hueco it's going into, `Armor.use(player, target_slot=None)` takes an explicit `target_slot` — `Inventory._handle_selection()` passes the chosen `filter_slot` through for any `Armor`, and `use()` falls back to `self.slot` when `target_slot` is omitted (always correct for the non-ring 1:1 slots). Two rings must have **different names** to be worn simultaneously — `Inventory.add_item()`'s existing "duplicate `Weapon`/`Armor` name auto-sells" rule isn't special-cased for rings, so two copies of the *same* ring can't both be equipped.
- `enemies/`: one file per enemy (20 total — the original 14 backbone plus 6 added in v0.14.0-c to flesh out Los Yermos to its GDD §4.6 roster: `rata_gigante.py`, `goblin_montaraz.py`, `chaman_goblin.py`, `salteador.py`, `ogro_del_yermo.py`, `el_carnicero.py`), each subclassing `Enemy` and overriding `perform_turn()`/`drop_item()` for unique mechanics. Common patterns reused across several enemies: a periodic/random "extra hit" that bypasses the normal turn (Huargo's pack bite, Gárgola's charge, Gólem's unavoidable earthquake, Nigromante's/Demonio's summoned ally, Salteador's second strike), a self-heal-under-threshold loop (Mago, Ángel Caído, Chamán Goblin — the first two learned the hard way that healing + high speed feed back into each other, see `TODO.md`), and an applied-debuff special attack that goes through `resolve_hit()` first (Bandido's `desarmado`, Espíritu Vengativo's/Chamán Goblin's `maldicion`, Demonio's `confusion`, Rata Gigante's/Goblin Montaraz's on-hit `veneno`/`sangrado` chance, Ogro del Yermo's stun). **Los Yermos (v0.14.0-c, GDD §4.6)**: 10 enemies now, tiers sized against `characters/power_budget.py`'s curve before writing their code (derivation + numbers in `docs/design/presupuesto_de_poder.md`). Goblin stays the literal first unlock (the early XP curve is calibrated around it) even though its design tier (2) is below Rata Gigante's (1); the chain is `Goblin → Rata Gigante → Goblin Montaraz → Huargo → Chamán Goblin → Esqueleto → Bandido → Salteador → Ogro del Yermo → El Carnicero (guardián) → Orco` (unchanged from there on). Two mechanics were revised from the initial design after user feedback: Goblin Montaraz's ranged attack uses the **same** `resolve_hit()` as everything else — an earlier draft partly ignored the player's evasion for it, which the user pointed out was backwards (a projectile should be *easier* to dodge than a melee hit, not harder), so it rolls a bleed chance instead; and Salteador's gold theft (`_steal`) is capped to `min(player.inventory.gold, randint(3, 8))` and gated behind a ~25%-of-turns chance (an *alternative* to attacking, not an add-on to every hit) so it can never leave the player at negative gold or feel like it procs "all the time". El Carnicero's enrage (`on_turn_end`, below 40% HP) is **one-way** — unlike the Orco's cyclical fury, once triggered it stays on for the rest of the fight.
- **Elemental weapon damage** (separate from the Mago's magical damage above — this is a *physical* mechanic): driven entirely by the affinity model in the Combat section (`combat/elements.py` + `Enemy.WEAKNESSES`/`RESISTANCES`/`IMMUNE_ELEMENTS`). `Enemy.take_damage(damage, defeated_enemies=None, element=None)` multiplies `damage` by `affinity_for({element})` (and consagrado ×1.25 / fractura_magica magic-resist→0), then applies multiplicative mitigation. The element comes from `Player.get_equipped_element()` (weapon, or brazales as fallback; skipped while `desarmado`). Elements are bare strings — no central registry beyond `combat/elements.py::ELEMENTS`. `combat/battle.py::_execute_turn` prints the affinity note (super-effective / resisted / immune) via i18n keys before the damage line. All `Enemy` subclasses (including `Skeleton`) share the exact same `take_damage()` signature, which is what lets `_execute_turn` call it directly.

**Items (`items/`)**: `item_base.py` defines only the abstract `Item` class. `factory.py` holds `item_factory(data)`, a dict → class dispatcher used by save/load to reconstruct items from JSON (`type` field selects the class: `HealingPotion`, `StatBuffPotion`, `RegenPotion`, `AntidotePotion`, `Material`, `Weapon`, `Armor`) — it imports the concrete classes at module level (no circular import, since `item_base.py` doesn't import `factory.py`). Every concrete item class implements `to_dict()`/`from_dict()` matching this factory — when adding a new item type, register it in `_ITEM_CLASSES` and implement both methods or save/load will silently drop it.
- `equipment.py`: `Weapon` (damage + optional `element`) and `Armor` (a `slot` from `ARMOR_SLOTS` + any mix of `defense`/`max_health`/`magic_resist`/`crit_chance`/`crit_damage`/`damage`/`element`/`regen`/`speed`/`precision`/`evasion`/`resist`), equipped via `Inventory.equip_menu()`. `resist` (added v0.11.0-b) is `dict[str, float]` — % damage reduction per element, e.g. `{"sagrado": 0.10}` — summed by `Player.get_total_resist(element)` and applied in `Player.take_damage()` before armour/magic-resist mitigation; unrelated to the enemy-side affinity model (`WEAKNESSES`/etc.), which stays the enemies' own defence. `Armor.from_dict()` defaults missing `"slot"` to `"peto"` for saves written before slots existed (see `persistence/save_load.py` below). Also holds `slot_accepts()`/`slot_label()` (see the ring note above) and `SLOT_LABELS` (display-only overrides for the awkward-looking slot keys — `"anillo1"` → `"Anillo 1"`, etc.).
- `potions/`: `potion_base.Potion` (abstract) + `healing_potion.py`, `buff_potion.py` (temporary stat buffs tracked in `player.active_effects`, decremented in `on_turn_end`), `regen_potion.py`, `antidote_potion.py` (`AntidotePotion` — removes every `status_effects` entry whose name is in `CURABLE` = poison/burn/paralysis/freeze; `use()` returns `False` when there's nothing curable so it doesn't consume a turn/stack).
- `materials.py`: crafting materials, non-usable directly (`use()` always returns `False`) — consumed instead by `crafting/forge.py` recipes.

**Inventory (`inventory/inventory.py`)**: `show_inventory()` prints the player's current/max HP right under the title (so it's easy to judge whether a healing potion is worth using) before listing items. Consumables stack via a `quantities` dict keyed by item name; `Weapon`/`Armor` don't stack — picking up a duplicate auto-sells it for gold instead. `show_inventory(filter_class, filter_slot=None, mode)` is reused both for read-only viewing and interactive selection (`mode="use"`); `filter_class` narrows to `Weapon`/`Armor`, `filter_slot` further narrows an `Armor` listing to a single equipment slot (e.g. only guantes) — both flow through to `_handle_selection()`, which rejects an item whose `slot` doesn't match `filter_slot`. All `Item.use()` implementations return `True` on success, which `_handle_selection()` relies on to decide whether to decrement a consumable from the stack and, in combat, whether the action consumes a turn (`"objeto_usado"`); when adding a new item type, make sure `use()` returns `True`/`False` accordingly. `Inventory.sell_item(item)` (used by the shop) removes one unit via the shared `_remove_one()` helper and credits `item.value` gold — refuses to sell anything currently equipped, checking both `equipped_weapon` and every slot in `equipped_armor`. `has_item(name, quantity)`/`consume_item(name, quantity)` look up and remove stock **by name** rather than by object reference (unlike `_remove_one()`) — used by the crafting system, which knows *what* material it needs but doesn't have a handle to the player's actual item instance.

**Shop (`shop/shop.py`)**: `Shop` holds a fixed, in-memory `catalog` of `ShopItem` (an item template + buy price); wired into Piedrablanca's "Mercado" sub-location via `ui/exploration.py::_open_shop()` → `Shop().open(player)` (moved out of the old flat menu in v0.12.0-c — see the Zone exploration loop section above). Buying clones the template through `items/factory.py::item_factory(template.to_dict())` (so each purchase is an independent instance) and calls the existing `Inventory.add_item()`; selling lists `player.inventory.items` and calls `Inventory.sell_item()`. The catalog is static code, not persisted — `persistence/save_load.py` doesn't know about it. `ShopItem.__str__()` appends `template.get_stats_info()` (same pattern as `CraftingRecipe.__str__()`) so weapons/armor show their actual numbers in the buy menu, not just flavor text — potions "worked" even before this by coincidence, since their `description` already spells out the numbers in prose (e.g. "Restaura 20 HP").

**Crafting (`crafting/forge.py`)**: `Forge` mirrors `Shop`'s structure — a fixed `recipes` list of `CraftingRecipe` (materials-by-name + gold cost + a result item template, cloned the same way as `ShopItem` via `item_factory`), wired into Piedrablanca's "Herrería" sub-location via `ui/exploration.py::_open_forge()` → `Forge().open(player)` (v0.12.0-c, same relocation as the Shop above). `CraftingRecipe.can_craft(player)` checks gold and `Inventory.has_item()` for every required material; `Forge._craft()` only mutates state (deduct gold, `Inventory.consume_item()` each material, `Inventory.add_item()` the result) after confirming `can_craft()`. 15 recipes exist: 11 `Armor` recipes (one or more per armor slot — peto, hombreras, brazales, guantes, cinturon, perneras, botas, amuleto, plus 3 different anillo recipes) and 4 `Weapon` recipes — "Daga Envenenada" (`"veneno"`, an alternate path alongside the Huargo's drop) plus, since v0.11.0-b, "Espada Consagrada"/"Daga Umbría"/"Vara Arcana" (`"sagrado"`/`"oscuridad"`/`"arcano"` — the first player-obtainable weapons for those 3 elements, deliberately lower damage than a same-tier normal weapon per the established elemental-weapon pattern below). Three existing `Armor` recipes also gained a `resist` bonus in v0.11.0-b (Cinturón de Resistencia → arcano, Amuleto de Resistencia → oscuridad, Anillo de Vitalidad → sagrado), picked for thematic fit with their existing materials/description rather than new drops. Collectively they consume all 14 materials from `characters/enemies/*::drop_item()` (one per enemy) — see the recipe list in `Forge.__init__` for exact costs/bonuses. Quantities are deliberately large (15-25 for most materials, down to 2-8 for the rarest drops like Piel de Troll/Esencia Arcana/Escama de Dragón) so that crafting requires actually farming the source enemy rather than a single lucky kill. None of the crafted items grant a passive-effect-per-turn (equipped items have no such hook in the combat loop) — "Armadura Regenerativa" is a plain stat boost despite the name, not literal regeneration. Crafted items are deliberately not always the best option for their slot: e.g. "Cinturón de Resistencia" trades the Gólem drop's raw armor for `magic_resist` instead, so the two aren't strictly comparable (see `TODO.md` for the loot-variety pass that shaped this — every slot now has 2+ drop sources with contrasting stats, not just a single "best" item, on top of its crafting recipe).
- **Recipe discovery**: `Forge.open()` only lists recipes whose materials the player has picked up at least once — `Inventory.discovered_materials` (a `set[str]`) is updated in `add_item()` whenever a `Material` is added, and stays populated even after the material is later consumed crafting. `CraftingRecipe.is_discovered(player)` checks membership for every required material name. This is separate from `can_craft()` (gold + current stock) — a discovered recipe can still be un-craftable if you've spent the materials. Persisted in save/load as `discovered_materials`; old saves without that key backfill it from whatever `Material` items are present in the save at load time.

**Equipping armor (`ui/menus.py::_equip_armor_flow`)**: the "Equipar Armadura" menu option opens a slot-picker submenu (same interactive-loop pattern as `Shop`/`Forge`) listing all 11 `ARMOR_SLOTS` with whatever's currently in each, then calls `player.inventory.equip_menu(Armor, filter_slot=<chosen slot>)` for the chosen one. Since v0.14.x (feedback del usuario), an occupied slot shows the item's name colored plus its `get_stats_info()` right next to it (same helper already used for loot lines and, since the same feedback round, `Player.show_stats()`'s own `--- Equipamiento ---` list) — so the player doesn't have to unequip/re-equip or check the shop to remember what a piece actually grants.

**Bestiary (`ui/menus.py::_bestiary_flow`, progressive since v0.14.0-a, GDD §7.2)**: read-only, lists **only** the enemies already in `defeated_enemies` — an unlocked-but-undefeated enemy doesn't appear at all, not even redacted. Picking one builds a throwaway instance via `_get_enemy_instance()` (so its stats reflect the class defaults, not leftover HP from a past fight) and prints `ui/formatting.py::print_bestiary_entry(enemy, kill_count)`, whose sheet **reveals itself by tiers of `Player.enemy_kill_counts`** (constants `BESTIARY_BASIC/COMBAT/AFFINITY/DROPS` = 1/3/5/10): **1** — kill count, a lore line, HP, attack range, the elements its attacks deal, gold; **3** — armour / magic resist, speed, precision / evasion, crit, penetration, regen and its signature ability; **5** — weaknesses / resistances / immune elements, the statuses it can inflict on you and its status immunities; **10** — the drop table. Below the next tier a grey hint reads "Derrótalo N veces para descubrir más". (Precision/evasion/penetration/regen were not assigned a tier by the GDD; they ride with tier 3.) The per-enemy data are **class attributes on `Enemy`** (empty defaults in `enemy_base.py`, filled by all 20 enemies): `DESCRIPTION` (lore line), `SIGNATURE` (its mechanic in one sentence), `ELEMENTS_DEALT` (`frozenset` of elements its attacks deal — Mago's four spells, Nigromante oscuridad, Ángel Caído sagrado, Demonio / Dragón fuego; most enemies deal none) and `INFLICTS` (`frozenset` of statuses it can apply to the player — desarmado, maldicion, confusion, quemado, paralizado, veneno, congelado). Status names in the sheet go through `i18n.t("status.<name>")`; the catalog gained `desarmado` / `confusion` / `maldicion` for it. The lore line is printed with `colorize(..., tint=False)` so words like "quemado" aren't tinted. **The drop table is derived, not duplicated**: `Enemy.drop_table()` runs the real `drop_item()` under `mock.patch.object(random, "random", ...)` with a float subclass whose `<=` / `<` always returns True and records the threshold it was compared with, then `zip(items, thresholds, strict=True)` — so the sheet can't drift from the code. It relies on the pattern every `drop_item()` follows today, `if random.random() <= p: items.append(...)` (one item per roll); a future enemy that breaks it makes `zip(strict=True)` raise, and `tests/test_bestiary.py` (which checks the table against a forced-success `drop_item()` for the whole roster) catches it. `Player.enemy_kill_counts` (a `dict[str, int]`) is incremented in `combat/battle.py::_handle_victory()` on **every** win, unlike `defeated_enemies`, which only records the first.

**Encounter flavor text (`combat/battle.py::_announce_encounter`, v0.14.x, GDD §8.1 follow-up, feedback del usuario: "estilo Pokémon")**: a short, non-branching line of atmosphere printed right before a battle starts — not a dialogue engine like `world/npc.py`, no choices, no state machine. Driven by 3 new class attributes on `Enemy` (`enemy_base.py`): `ENCOUNTER_KIND` (`"normal"` default / `"elite"` / `"guardian"`), `ENCOUNTER_LINE` (the line shown the first time you ever face this specific enemy), `TAUNT_LINES` (a tuple of provocations, elite/guardian only, one picked at random each time). Classification reuses what already existed instead of inventing a new criterion: the 5 `elite` enemies are exactly `audio/resource_manager.py::HARD_BATTLE_ENEMIES` (Gólem de Piedra, Mago, Nigromante, Ángel Caído, Demonio); `guardian` is El Carnicero (opens the Bosque) and the Dragón (final boss) — the other 13 stay `"normal"`. Behaviour: the very first encounter with an enemy always shows `ENCOUNTER_LINE` (a plain "wild-encounter"-style sentence for normal enemies, deliberately more ominous for elite, "aún más" for guardian); from the 2nd encounter onward, only elite/guardian say anything else, and only if the player has *lost* to that specific enemy at least once (a normal enemy never taunts, and an elite/guardian you haven't lost to yet goes straight to battle in a repeat encounter). Fires from both Explorar and Cazar — it describes facing the enemy, not how you found it. Persistence reuses `player.mundo["banderas"]` (no save-schema change): `_seen_flag(enemy)` (`"vio_a_<nombre>"`) is set by `_announce_encounter` itself the first time it prints; `_defeat_flag(enemy)` (`"perdio_contra_<nombre>"`) is set by `_handle_defeat(player, enemy, ...)` (now takes the enemy, optional for backward compatibility) only when `enemy.ENCOUNTER_KIND != "normal"`. Called from `_run_one_battle` right before the "¡Ha comenzado la batalla...!" line, gated the same as the rest of that screen's flavor (`start_auto != "turbo"` — hidden during Turbo farming). Whenever it actually prints a line (intro or taunt — a normal-enemy repeat encounter prints nothing and skips this too), it pauses with a "Presiona Enter para continuar..." right after (feedback del usuario: otherwise the line flashes by and gets buried under the "¡Ha comenzado la batalla...!" banner that follows immediately). `tests/test_battle.py` covers first-vs-repeat for a normal enemy, the elite taunt only unlocking after a loss, `_handle_defeat` only flagging non-normal enemies, Turbo suppression, the pause firing only when something was printed, and an end-to-end real battle.

**Power budget tool (`characters/power_budget.py`, v0.14.0-b, GDD §4.4)**: not a game screen — a design tool, used when writing a zone's roster (v0.14.0-c onward) to check a new enemy's rough tuning before writing its code. `power_score(stats) = max_health × speed × net_damage`, `net_damage = mean_damage × (1 + crit_chance × (crit_damage - 1))`; deliberately does **not** subtract a reference player's mitigation (no fixed "typical" player exists — class/level/gear all vary — so subtracting something here would be more speculative than subtracting nothing; whether it lands against a real player is what the playtest step after design confirms). Known blind spot: the formula only sees `min_atk`/`max_atk`, so mechanics that add threat without raising those (self-heal, revive, inflicted debuffs) aren't captured — Esqueleto (revives once at half HP) and Mago (heal + control, deliberately low base attack) are the two known cases among the 14. `target_score(zone_index, tier) = BASE · ZONE_GROWTH^zone_index · TIER_GROWTH^(tier-1)` (`zone_index` = position in `world.map.ZONE_ORDER`, tier 1-10 within a zone) — geometric on both axes, constants fit by log-linear regression against real data (`ZONE_GROWTH` against the 6 already-populated zones' average power; `TIER_GROWTH` against the only zone with GDD-fixed tiers, Los Yermos §4.6: Goblin=2, Huargo=4, Esqueleto=6, Bandido=7 — no other zone has design tiers yet, so none are invented here; that's for whichever sub-phase fills that zone), then rounded to `BASE=1500`, `ZONE_GROWTH=2.1`, `TIER_GROWTH=1.25`. `zone_score_range(zone_index)` returns `(target(zone_index, 1), target(zone_index, 10))` — the valid power band for *any* enemy of that zone, usable without knowing its exact tier (every zone but Los Yermos, today). `deviation(actual, target)` is a signed fraction. **Not retroactive**: the 14 backbone enemies were tuned by playtest before this tool existed and are not forced to fit it now (`tests/test_power_budget.py` documents which ones land outside tolerance and the known reason — see the full report in `TODO.md`); the tool exists to guide *new* content going forward.

**Dialogue engine (`world/npc.py`, v0.13.0-a, GDD §8.2)**: frozen dataclasses + pure functions, no printing/asking of its own — `play_conversation(conversation, player, show, pick, notify)` takes three callbacks (`show(text)`, `pick(option_texts, done_flags) -> index`, `notify(message)`), so it's fully unit-tested and `ui/exploration.py` only supplies `print`/`input`. Model: `NPC(id, name, zone_id, conversations, idle_lines)` → `Conversation(id, start, nodes, trigger: Condition, repeatable)` → `DialogueNode(id, text, choices, next, effects)` → `Choice(text, next, condition, effects, reply)`. A node with no `choices` is linear (shows its text then follows `next`, or ends); a node whose choices are all hidden by conditions ends the conversation. `Condition` (`requires_flags`, `forbids_flags`, `min_level`; empty = always met) gates both a conversation's trigger and individual replies against `player.mundo["banderas"]`/`player.level`. `Effect` kinds: `set_flag`, `give_gold`, `give_item` (an `Item.to_dict()` dict rebuilt via `item_factory`; helper constructors `set_flag()`/`give_gold()`/`give_item()`); **Node `effects` run when the node is shown** (before the replies are offered) — use them for anything the NPC hands over, so the player sees "Recibes X" *before* choosing how to react (playtest fix: a gift announced after the reply felt odd). **`Choice.reply`** is what the NPC says right after a reply is picked; a reply that ends the conversation (`next=None`) must have one or the player says goodbye to a silent NPC — enforced by `tests/test_npc.py` over the real content (`choice.reply` asserted for every closing choice), so new content can't regress it. `apply_effects()` returns the notification strings and raises `ValueError` on an unknown kind. `NPC.next_conversation()` returns the first conversation (in declared order) whose trigger is met and that is either `repeatable` or not yet in `mundo["dialogos_vistos"]`; `talk()` plays it, or falls back to a random `idle_lines` entry (default "No tiene nada más que decirte."). **Conversations are re-enterable (v0.13.0-a playtest change):** every time the player finishes a path, the last reply picked is recorded in `mundo["dialogos_vistos"]` as `"<conv>/<node>/<choice index>"`; the next visit shows the tree again and `pick` gets a `done` flag per reply (the UI draws a green ✔ to the right of it). A reply is *done* if it is a closing reply already picked, or leads to more replies that are all done (`_choice_done`/`_all_done`, recursive, cycle-safe; replies hidden by their `Condition` don't count). A non-repeatable conversation is added to `dialogos_vistos` (and the NPC falls back to idle lines) only once its whole tree is done (`_all_done` from the start node; a purely linear conversation is done after one play). Effects that give something (gold/items) run only once per save via a `"<key>#efectos"` marker (`_apply_once`; flag-only effects are idempotent and unrecorded) — but re-showing the node text after that would be misleading, so content should also hide the branch with a `Condition` (Yerma's potion branch is gated by `forbids_flags=("recibio_pocion_yerma",)`, which its node sets). Trade-off: revisiting shows the start node's greeting again. GDD rule "choice nodes offer ≥3 responses" is not enforced by the dataclasses but by `tests/test_npc.py` over the real content. NPCs are declared per zone: a `world/data/<zone>.py` module may expose `NPCS = (NPC(...), ...)`; `world/map.py` aggregates them into `NPCS: dict[id, NPC]` and `npcs_in_zone(zone_id)`; a test asserts each NPC's `name` appears in its zone's `Zone.key_npcs`. **NPC content (v0.13.0-b, GDD §3 zone table):** 9 NPCs, each with a first-meeting story conversation (3 nodes, 7 closing replies, sets `conocio_a_<npc>` from the root node's effect), one follow-up conversation whose `trigger` requires *another* NPC's `conocio_a_*` flag (a cross-reference web that rewards exploring and backtracking: Halbrand←Cael, Dorn←Mirelle, Nia←Halbrand, Cael←Mirelle, Mirelle←Oren, Oren←Kort, Kort←Sella, Sella←Aldric, Aldric←Kort) and 3 idle lines. Cast: Piedrablanca — Yerma (tavern; the v0.13.0-a conversation), Halbrand (guard captain, bandits), Dorn (hunter; a Troll-hide errand seeded via `dorn_encargo_troll`, gives 20 gold once), Nia (lost doll); Los Yermos — Cael (the Brecha and the altar; sets `sabe_del_altar`); Bosque — Mirelle; Ciénaga — Oren (ferryman, invented for the zone the GDD left empty; gives 25 gold once); Cañón — Kort (gives a Poción de Salud once); Torre/Necrópolis — Sella (sets `sella_tomo_pista`, the seed of *El tomo prohibido*); Ciudadela — Aldric. Gift branches are gated with `forbids_flags` exactly like Yerma's potion. The GDD's own text disagrees with its table in two places (Mirelle in Act IV vs. the Bosque; Dorn's errand listed under the Bosque though he lives in Piedrablanca) — the table won. `end(text, reply, *effects)` in `npc.py` is a shortcut for a reply that closes the conversation. Extra content tests in `tests/test_npc.py`: every zone's `key_npcs` matches its defined NPCs, every `requires_flags` is set by some conversation, every NPC can be exhausted with all flags pre-set (gifts given once), and gift branches disappear once taken.

**World package (`world/`)**: `world/zone.py::Zone` is a frozen dataclass (`id`, `name`, `theme`, `enemies`, `sub_locations`, `key_npcs`, `is_hub`), one instance per zone in `world/data/<zone>.py` (mirrors `characters/enemies/` — one file per unit of content). `world/map.py` collects them into `ZONE_ORDER` (tuple, the linear chain from the GDD §3 diagram, `"piedrablanca"` first) and `ZONES` (`dict[str, Zone]`). Only the 20 already-implemented enemies are assigned to zones today (`GDD §4`'s full ~70-enemy roster is future design; Los Yermos is complete at 10 since v0.14.0-c, the other 5 populated zones still have their original 2-3 backbone enemies each); a zone with an empty `enemies` tuple (Piedrablanca the hub, or a zone whose roster isn't designed yet, e.g. Ciénaga de los Ahogados) is intentional, not a bug. **`is_hub` (v0.14.x, feedback del usuario) distinguishes those two "empty" cases**, since `ui/exploration.py` used to treat them the same way and let the player "explore" into combat inside Piedrablanca — a village the GDD explicitly calls "hub, no enemies". `True` only for Piedrablanca today; `_zone_candidates()` returns `[]` unconditionally for a hub (no falling back to "any unlocked enemy"), while a zone with a genuinely undesigned roster (Ciénaga) still falls back so Explorar doesn't dead-end there. `tests/test_world.py::test_only_piedrablanca_is_a_hub` guards against a future zone accidentally inheriting it. Four helpers, all pure functions with no gameplay side effects of their own:
- `zone_for_enemy(name)` — which zone a backbone enemy belongs to, `None` if unassigned.
- `default_zone_for_progress(defeated_enemies)` (v0.12.0-a) — infers a save's current zone from combat progress for the v1→v2 save migration; walks `ZONE_ORDER`, skipping zones with no roster yet, stopping at the first zone with no backbone enemy defeated.
- `next_zone(zone_id)` (v0.12.0-b) — the immediate next zone in `ZONE_ORDER`, or `None` past the last one. Used by `ui/exploration.py::_travel_flow` to offer only the *next* hop as "frontera", never skipping ahead.
- `is_zone_reachable(zone_id, unlocked_enemies)` (v0.12.0-b) — `True` if `zone_id`'s first backbone enemy is unlocked, or unconditionally `True` for a zone with no roster yet (nothing to gate it on).

**Save/load (`persistence/save_load.py`)**: game state is serialized to JSON, then base64-encoded, written to `saved_games/<player_name>.sav`. Saving always backs up the previous file to `<player_name>.bak` first; loading falls back to the `.bak` file if the `.sav` fails with an error *not* in `{json.JSONDecodeError, binascii.Error, UnicodeDecodeError, KeyError}` (those specific failures return `None` immediately without a fallback attempt — this is existing, deliberately-preserved behavior, not something to "fix" silently). Item reconstruction goes through `items/factory.py::item_factory`. `equipped_armor` is saved as `{slot: item_dict_or_null}`; on load, a dict containing a `"type"` key (the pre-slots format, a single armor item) is treated as legacy and placed into the `"peto"` slot — this is the only place in the codebase that has to distinguish old vs. new save-file shapes rather than just defaulting missing keys. **`mundo` block (save schema v2, GDD §9.4)**: `Player.mundo` is a plain dict — `zona_actual`, `zonas_visitadas` (list), `misiones`, `banderas` (`set`), `dialogos_vistos` (`set`), `diario` (list), `arena_mejor_oleada`. Added in v0.12.0-a ahead of any gameplay using it (so the save format wouldn't need a second migration); `zona_actual`/`zonas_visitadas` are now live, read and written every turn by `ui/exploration.py::zone_loop()`/`_travel_flow()` (v0.12.0-b) — `banderas`/`dialogos_vistos` are live since v0.13.0-a/b (dialogue) and `diario` since v0.13.0-c (lore notes); `misiones` and `arena_mejor_oleada` are still unused, waiting on quests/Arena. Sets aren't JSON-serializable, so `save_game()` writes `banderas`/`dialogos_vistos` as sorted lists and `load_game()` reconstructs them as `set`s. Migration v1 → v2: a save with no `"mundo"` key gets `zona_actual` inferred via `default_zone_for_progress()` and `zonas_visitadas` backfilled to every zone in `ZONE_ORDER` up to and including it; everything else starts empty.

**Audio (`audio/resource_manager.py`)**: `ResourceManager` is a singleton (`__new__` override). Music tracks go through the dedicated `pygame.mixer.music` stream (one track loaded/playing at a time, loaded on demand from `music_paths[name]` in `play_music()`); SFX are separate `pygame.mixer.Sound` objects played on the regular channel pool via `play_sfx()`. This split matters: `pygame.mixer.music.get_busy()` only reflects the music stream, so an SFX playing concurrently (e.g. a hit sound mid-combat) never masks "the track has ended" — using `pygame.mixer.get_busy()` (any channel) here was a real bug fixed in a past session, since a busy SFX channel could block the mood system from ever detecting the track had finished. It self-manages background music via a `mood` field (`"adventure"` vs `"battle"`) — `update()` only acts once `pygame.mixer.music.get_busy()` is `False` (current track ended), picking a new one via `play_random_adventure_music()` or `play_battle_music(target_enemy)`. `combat/battle.py` calls `rm.enter_battle(enemy_name)` / `rm.exit_battle()` (once per battle, not per fight in a chain): `enter_battle` only switches — to `mood="battle"` + `play_battle_music()` — when `has_dedicated_battle_music(enemy_name)` (the final boss or the 5 hard late-game enemies in `HARD_BATTLE_ENEMIES`); against a standard enemy it leaves the current track alone (short/chained fights would otherwise restart the music constantly). `exit_battle` only forces a fresh adventure track if it's leaving dedicated battle music. When zone elites/guardians exist, `has_dedicated_battle_music` is the single switch to move (see `TODO.md`). `update()` is called from `app.py::main()` once at startup, from `main_menu()`'s and `ui/exploration.py::zone_loop()`'s loops, from inside `initiate_battle()`'s turn loop, and — since this is a synchronous console app that spends most of its time blocked on `input()` — from a daemon thread (`app.py::_music_watchdog`) that calls it every 2s so tracks still auto-advance while the game is just waiting on the player. Volumes persist to `config.ini` via `config/settings.py`. `audio/catalog.py` holds the `AUDIO_ASSETS` dict of relative asset paths.

## Tests (`tests/`)

`pytest`-based, ~685 tests, coverage ≥90% of the measured code (see the Coverage note above). `items/factory.py::item_kind_label(item)` gives the display type label ("arma · fuego", "armadura · casco", "poción", "material de herrería") used by loot listings. `tests/conftest.py` sets `SDL_AUDIODRIVER`/`SDL_VIDEODRIVER=dummy` and provides the shared fixtures: `_headless_audio` (session-scoped autouse — inits `pygame.mixer` so `ResourceManager`/`battle.py` run without audio hardware), `player` (a fresh `Player` used by almost every test), `weak_enemy` (a 1-HP Goblin for deterministic combat outcomes), and `tmp_save_dir` (monkeypatches `save_load.SAVE_DIR` to a tmp dir).

Testing conventions:
- **Interactive code is driven by monkeypatching `console.ask`** at the module under test, e.g. `monkeypatch.setattr("valeterna.shop.shop.console.ask", ...)`; queue a sequence of answers with an `iter(...)` when a flow asks more than once.
- **`random.random`/`randint`/`choice` are one shared stdlib object process-wide** — `characters/stats.py::resolve_hit`, `enemy_base.py` and each enemy module all call the same function, so a monkeypatch of `"random.random"` affects every roll in that turn. Tests fix an extreme value (`0.0` → everything hits/procs, `0.99` → misses) and assert *effects* (health dropped, status applied), not exact damage numbers. The one enemy test file that needs per-roll control (`test_new_enemies.py`) documents the real roll order in a comment.
- Enemy `perform_turn()` / `_cast_*` / `_claw_attack` helpers are tested directly (call the helper, don't route through a whole battle).

Which file tests what: `test_stats` (clamping, `resolve_hit`), `test_player` (combat math / status / leveling), `test_classes` (per-class stats / growth / magical attack / save round-trip), `test_skills` (catalog / passives / active effects / cooldowns / equip cap), `test_battle` (`initiate_battle` outcomes, elemental bonus), `test_elements` (affinity multipliers), `test_elemental_reactions` (shatter/combustion), `test_enemy_status` (status processing on enemies), `test_i18n` (catalog fallback), `test_new_enemies` + `test_original_enemies` + `test_enemy_attacks` (per-enemy `perform_turn` mechanics), `test_inventory` / `test_items` / `test_potions` / `test_shop` / `test_crafting` / `test_armor_progression`, `test_save_load` (incl. the `mundo` block round-trip and v1→v2 migration), `test_npc` (conditions, effects, tree traversal, one-time vs repeatable, idle fallback, and structural validation of every real NPC/conversation), `test_lore` (notes, Diario, real-content checks), `test_bestiary` (reveal tiers, `drop_table()`, every enemy's sheet), `test_power_budget` (the formula, the target curve, the report), `test_los_yermos_10` (the 6 new enemies' mechanics), `test_world` (`Zone`/`ZONES`/`ZONE_ORDER` consistency, `zone_for_enemy`, `default_zone_for_progress`, `next_zone`, `is_zone_reachable`), `test_exploration` (zone loop: Explorar's weighted roll, Viajar's fast-travel/frontier, the Personaje sub-menu's `"volver_menu"` signal — same monkeypatch-`console.ask` convention as `test_menus`), `test_formatting`, `test_audio`, `test_settings`, `test_secret_store`, `test_crash_logging`, `test_crash_reporting`, `test_app_boot` (smoke test — `app.main()` boots and exits cleanly).

## Known incomplete/dead areas (see TODO.md)

- Combat is strictly 1-vs-1: there's no real concept of multiple simultaneous enemies. Several enemies fake it with an "extra hit" pattern instead (a summoned ally or pack member attacks immediately as part of the same turn, rather than existing as a separate combatant with its own gauge/turns) — see the `enemies/` bullet above.
- Equipment set bonuses (2/4/6-piece bonuses for wearing multiple items from the same themed set) are a planned feature, discussed with the user but not yet designed or started — today every armor piece is independent, no `set` concept exists on `Armor`.
- `TODO.md` tracks the detailed history of balance passes (per-enemy playtest numbers, why specific stat values were chosen) — worth checking before re-tuning an enemy or item, since the reasoning (and the pitfalls already hit) is usually documented there rather than in code comments.
